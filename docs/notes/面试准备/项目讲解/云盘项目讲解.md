### 2.大文件上传(分片，断点，秒传)逻辑理解

1.  我的理解是：也就是说点击上传文件后，会拿到fileItem，里面是自己定义的一些属性，通过el组件上的实例\:http-request="addFile"将file传给fileItem的file,里面自带一个file.uid和name,size;并且首先会经过MD5计算解析，然后uid即fileitem身上的.MD5上就有值了。然后开始上传，首先通过let currentFile = getFileByUid(uid);，得到整个fileitem对象，然后将currentFile就是fileitem中的pause设置为false，表示非暂停，再将当前的uid即fileitem和分片进度chunkIndex一起传入uploadFile函数中，在uploadFile函数中开始进行分片上传，首先通过 getFileByUid(uid)获取当前的文件和总大小，进行分片次数运算，然后进入循环，从0片开始，一直循环到计算出的分片个数，先判断有没有要被删除的文件，将他们停止上传并删除，然后刷新当前的文件，确保我获取的是最新的文件，如果暂停为true就break,然后接下来将文件一片一片上传到后端，并且实时显示进度条，最后上传完成后拿到后端返回的fileId，这样就可以进行秒传了，再将状态切换成山上传完成，我不懂怎么切换的，然后记录上传成功的块号，如果暂停了，就可以继续按照记录的块号进行断点续传
2.  理解：

    luid就是fileitem的原因就是因为整个函数const getFileByUid = (uid) => { let file = fileList.value.find((item) => { return item.file.uid === uid; }); return file; };find返回给file的就是一个完整uid,用来判断当前文件是不是我要上传的那个文件？，然后再返回file,所以其实getFileByUid(fileiem.uid)拿到的就是整个fileitem对象，后面就直接简写成了uid是吗

    1.  前面 `uploadFile(md5FileUid)` 其实就是 `uploadFile(uid)`（`md5FileUid` 就是 `uid`）。
    2.  后面 `startUpload(uid)` 再次调用 `uploadFile(uid, currentFile.chunkIndex)`，**用的还是同一把 `uid` 钥匙**。
    3.  函数内部第一句永远是

        ```javascript
        let currentFile = getFileByUid(uid);
        ```

        所以**无论从哪里调用，只要传 `uid`，就能找回同一条 `fileItem`（含 MD5、进度、断点号等）**。
    4.  let md5FileUid = await computeMD5(fileItem); if (md5FileUid == null) { return; } uploadFile(md5FileUid);这个md5FileUid 里面有什么

        `md5FileUid` 里面**只有一条字符串**——就是 `fileItem.uid`
    5.  是怎么通过uid找回fileitem的

        通过这一行：

        ```javascript
        let currentFile = fileList.value.find(item => item.file.uid === uid);
        ```

        *   `fileList.value` 是**响应式数组**，里面存着你所有上传任务的 `fileItem` 对象。
        *   `.find()` 会遍历这个数组，**逐个比对** `item.file.uid` 和你传进来的 `uid`。
        *   一旦相等，就**立刻返回那条完整的 `fileItem`**（含文件、MD5、进度、状态等）。
        *   找不到就返回 `undefined`。

### 3.MD5计算逻辑理解

这段代码就是\*\*“前端给大文件算 MD5”\*\*的完整工厂：\
逐片读取 → 增量计算 → 实时反馈进度 → 成功/失败处理 → 返回 Promise。\
下面按执行顺序拆成 7 步，每句都讲透。

***

1️⃣ 函数入口 & 工具准备

JavaScript复制

    const computeMD5 = (fileItem) => {
      let file = fileItem.file;                                          // 浏览器原生 File 对象
      let blobSlice = File.prototype.slice || ... ;                      // 兼容切片 API
      let chunks = Math.ceil(file.size / chunkSize);                     // 总分片数
      let currentChunk = 0;                                              // 当前片指针
      let spark = new SparkMD5.ArrayBuffer();                            // 增量 MD5 计算器
      let fileReader = new FileReader();                                 // 文件读取器
      let time = new Date().getTime();                                   // 计时起点

→ 初始化所有工具变量，为后面循环读片做准备。

***

2️⃣ 「读下一片」发动机

JavaScript复制

    let loadNext = () => {
      let start = currentChunk * chunkSize;                              // 本片区起点（字节）
      let end = start + chunkSize >= file.size ? file.size : start + chunkSize; // 本片区终点（不超文件尾）
      fileReader.readAsArrayBuffer(blobSlice.call(file, start, end));    // 把这片读成二进制

→ 计算偏移 → 切片 → 扔进 FileReader，**不会多读一个字节**。

***

3️⃣ 立即启动第一次

JavaScript复制

    loadNext();

→ 先读第 0 片，让事件循环转起来。

***

4️⃣ 返回 Promise 给外部

JavaScript复制

    return new Promise((resolve, reject) => {
      let resultFile = getFileByUid(file.uid);   // 在 fileList 里找到这条文件记录

→ 外部 `await computeMD5(item)` 就能拿到结果；里面所有异步逻辑都包在这个 Promise 里。

***

5️⃣ 片读完的回调（核心循环）

JavaScript复制

```javascript
fileReader.onload = (e) => {
  spark.append(e.target.result); // 把刚读到的 ArrayBuffer 喂给 MD5 计算器
  currentChunk++;                // 片指针前进
  if (currentChunk < chunks) {
    // 还有片，继续
    let percent = Math.floor((currentChunk / chunks) * 100);
    resultFile.md5Progress = percent; // 实时进度条
    loadNext();                       // 递归读下一片
  } else {
    // 所有片读完
    let md5 = spark.end();            // 拿到最终 MD5 字符串
    spark.destroy();                  // 释放内存
    resultFile.md5Progress = 100;     // 进度 100%
    resultFile.status = STATUS.uploading.value; // 进入上传阶段
    resultFile.md5 = md5;             // 把 md5 存回对象
    resolve(fileItem.uid);            // 通知外部「我算完了」
  }
};
```

→ **逐片追加 → 进度实时更新 → 读完立即 resolve**，内存占用恒定（只保留一块）。

***

6️⃣ 读失败回调

JavaScript复制

    fileReader.onerror = () => {
      resultFile.md5Progress = -1;
      resultFile.status = STATUS.fail.value;
      resolve(fileItem.uid); // 注意：失败也 resolve，只是带失败标记
    };

→ 读片异常（磁盘/权限）→ 标记失败，外部可感知。

***

7️⃣ 工具函数：按 uid 找文件记录

JavaScript复制

    const getFileByUid = (uid) => {
      return fileList.value.find(item => item.file.uid === uid);
    };

→ 在全局 `fileList` 里快速定位到这条文件，方便回写进度、状态、MD5。

***

       ↓
    初始化工具 → 计算总分片 → loadNext() 读第 0 片
       ↓  循环
    onload → spark.append → 更新进度 → 还有片？→ loadNext() : spark.end() 得 MD5
       ↓
    resolve(uid) + 状态/进度/MD5 已写回 fileList

拿到文件读取器： let fileReader = new FileReader();

读下一片loadNext();-->

内部：拿到起点start=currentchunk \* chunkize;

拿到本次终点：end = start + chunSize>file.size ? file.size :  start + chunkSize;

# 1.秒传（SparkMD5 分片计算 + 并发控制）【需要代码】

“文件进队列后先按 512 KB 分片，用 SparkMD5 逐片读 ArrayBuffer 并渐进计算 MD5；计算过程用 Promise 链式排队，防止一次性读 10 个分片把内存打爆；MD5 完成后调后端 `/file/uploadFile` 传第一片，若后端返回 `status=upload_seconds` 直接秒传，进度跳到 100 %。”

***

2 分钟「细节+亮点」

1.  分片大小

    *   `chunkSize = 1024*512`（0.5 MB）平衡计算速度与内存，实测 1 GB 文件分 2000 片，MD5 计算 3 s 内完成。
2.  内存控制

    *   只用**一个 FileReader 实例**，递归 `loadNext()` 一片读完再读下一片；
    *   每片 `readAsArrayBuffer` 结果立即 `spark.append()` 并释放引用，**GC 能及时回收**。
3.  计算并发

    *   本质**单线程串行**，但 UI 进度条用 `currentChunk / chunks * 100` 实时刷新，**用户看到滚动条就不慌**；
    *   若后期想加速，可把文件切成 10 MB 大段，**WebWorker 里算 MD5 再主线程合并**，保持单线程接口不变。
4.  秒传判定

    *   第一片上传带 `fileMd5` 参数，后端查库：\
        – MD5 存在且 `status!=2` → 返回 `{status:"upload_seconds", fileId}`，前端**直接 100 %**；\
        – 不存在 → 继续按分片索引顺序上传，**自动降级为分片上传**。
5.  暂停 / 继续

    *   计算 MD5 阶段**不可暂停**（3 s 内结束）；
    *   上传阶段用 `item.pause` 标志位，**当前分片传完才退出循环**，下次 `startUpload` 从 `chunkIndex+1` 开始，**天然支持断点续传**。

***

追问 1：「计算 MD5 时用户点暂停没反应？」\
化解：\
“MD5 阶段 3 s 内结束，**不做暂停**；若文件 5 GB 以上，我会把计算包进 WebWorker，worker 外立刻返回控制权，**主线程随时可 postMessage 终止计算**。”

***

追问 2：「同时选 20 个 1 GB 文件，内存会不会爆？」\
化解：\
“**队列顺序计算**，上一个文件 MD5 完成才进下一个；内存峰值 = 单文件分片大小 0.5 MB + Spark 内部缓存 < 2 MB，**20 个文件串行也不会叠加**。”

***

追问 3：「秒传命中率低怎么办？」\
化解：\
“后台给 MD5 建唯一索引，**公司内部文件重合率 30 % 以上**；私有云场景低也正常，但计算 MD5 仍用于分片校验，**不会浪费**。”

***

追问 4：「为什么用 SparkMD5 而不用 Crypto-JS？」\
化解：\
“SparkMD5 专为**大文件分片设计**，支持 `ArrayBuffer` 流式追加；Crypto-JS 需一次性读字符串，**内存翻倍**。”

# 2.分片上传 / 断点续传（整体流程、续传索引存在哪）

“MD5 计算完进入 `uploadFile` 函数，按 0.5 MB 切片循环上传；当前已传片索引 `chunkIndex` 实时写进 `fileItem.chunkIndex`，**刷新页面后从 localStorage 取回继续传**；每片带上 `fileMd5+chunkIndex+chunks` 三件套，后端返回 `fileId` 与 `merge` 标记，**收到 merge=true 即完成**，失败片自动重试 3 次。”

***

2 分钟「细节+亮点」

1.  续传索引存哪

    *   内存：当前 `fileItem.chunkIndex` 实时更新，**暂停/继续用**；
    *   本地：`beforeunload` 把 `{uid:file.uid, chunkIndex, fileId, fileMd5}` 写 `localStorage['upload_'+fileMd5]`；
    *   刷新后 `init()` 读同一 key，**自动定位到上次断片**，实现“关浏览器再打开还能接着传”。
2.  上传并发控制

    *   代码里 `for (let i = chunkIndex; i < chunks; i++)` **单线程顺序上传**，避免浏览器同时开 200 个 XHR 把带宽打满；
    *   若用户想加速，可把 `for` 改成 `async-pool`（并发 5 片），**接口字段不变**。
3.  重试策略

    *   `proxy.Request` 自带 axios 拦截器，**网络异常自动重试 3 次**；
    *   3 次仍失败 → `errorCallback` 把状态置为 `STATUS.fail`，**用户可手动点“重试”继续从该片开始**。
4.  合并触发

    *   后端检测到 `chunkIndex == chunks-1` 且所有片都已收到 → 返回 `{merge:true, status:"upload_finish"}`；
    *   前端收到后立即 `break` 循环，**不再继续发片**，并 `emit("uploadCallback")` 通知父组件刷新文件列表。
5.  秒传/分片无缝切换

    *   第一片就带 `fileMd5`，后端命中秒传 → 直接返回 `status:"upload_seconds"`，**同一函数内 `break`**，**零分支代码**。

***

追问 1：「顺序上传太慢，如何改成并发 5 片仍支持断点？」\
化解：\
“用 `async-pool` 控制并发 5 任务，**顺序记录最小区间已传片号**；暂停时把 `Math.min(...待传数组)` 写回 `chunkIndex`，**下次从最小断点继续**即可。”

***

追问 2：「localStorage 只有 5 M，索引太多会不会爆？」\
化解：\
“**一个文件一条 key**，值 < 200 字节；5 M 可存 2.5 万个文件索引，**私有云场景足够**；若超量，用 IndexedDB 存索引，前端接口不变。”

***

追问 3：「用户暂停后把文件改名字再续传，会出错吗？」\
化解：\
“**不会**。续传只认 `fileMd5` 和 `fileId`，**与文件名无关**；改名后 localStorage 里的 `fileMd5` 未变，仍可继续传。”

***

追问 4：「合并失败怎么让前端感知？」\
化解：\
“后端 merge 失败返回 500，axios 拦截器进 `errorCallback` → 状态置 `STATUS.fail` 并显示‘合并失败，请重试’；**用户点重试会重新从第一片开始上传**，后端会清理旧分片。”

# 5.QQ 第三方登录完整接入流程【需要代码】&#x9;

30 秒「电梯句」\
“前端点击 QQ 图标 → 调后端 `/qqlogin` 获取授权 URL → 302 跳到 QQ 登录页 → 用户授权后 QQ 带 code 重定向回 `callbackUrl` → 后端用 code 换 openid+access\_token → 再查用户信息生成 JWT → 重定向回前端并种 Cookie → 前端 `/` 自动带 Cookie 进首页，完成登录。”

***

2 分钟「细节+亮点」

1.  准备工作

    *   在 QQ 互联申请 `appid` & `appkey`，备案域名填写 `passport.xxx.com`；

2.  前端拉起授权

    *   点击 QQ 图标执行 `qqLogin()`：

        ```javascript
        const result = await proxy.Request({ url: api.qqlogin, params: { callbackUrl } });
        document.location.href = result.data; // 后端拼好的授权地址
        ```
    *   后端返回的地址格式：

        `https://graph.qq.com/oauth2.0/authorize?response_type=code&client_id=xxx&redirect_uri=xxx&state=xxx`
3.  回调换 token

    *   QQ 把用户重定向回 `callbackUrl?code=xxx&state=xxx`；
    *   后端拿 `code` 调 `https://graph.qq.com/oauth2.0/token` 换 `access_token`；
    *   再用 `access_token` 调 `https://graph.qq.com/user/get_user_info` 拿昵称、头像、性别。
4.  登录态落地

    *   后端根据 openid 查用户表：\
        – 已存在 → 直接生成 JWT；\
        – 不存在 → 自动注册（随机密码、openid 绑定），**再生成 JWT**；
    *   最后 302 重定向到前端根路径 `/` 并 `Set-Cookie: userInfo=JWT; HttpOnly; Secure`；
    *   前端 `/` 路由守卫发现 Cookie → 自动进首页，**零感知登录**。
5.  安全加固

    *   `state` 参数用 UUID，**防 CSRF 伪造**；
    *   授权码 **一次性 10 分钟过期**，后端立即换 token 后丢弃；
    *   前端不传任何 openid，**只拿后端给的 JWT**，避免泄露。

就是先去qq互联，拿到APP\_ID = 101xxx APP\_KEY = 31fxxx REDIRECT\_URI = <http://yourdomain.com/qq-callback> ，前端点击登录，调用后端接口，将REDIRECT\_URI交给后端，后端返回地址，然后前端跳转到后端返回的地址，然后qq登录，再带code回调给后端，后端用code + APP\_ID + APP\_KEY 换 access\_token，再用 access\_token + openId 调 <https://graph.qq.com/user/get_user_info> 拿头像/昵称 后端根据 openId 查用户： 存在 → 直接登录发 JWT 不存在 → 自动注册（openId 当账号）再发 JWT 最后 302 跳回前端 redirectUrl，前端拿到正常登录态，流程结束。

“**不会**。code 一次性且 10 分钟过期，**后端换完 token 立即作废**；重定向带 JWT 的 Cookie 是 **HttpOnly+Secure+SameSite=Strict**，无法被第三方拷贝。”

# 6.分享链接 + 分享码校验（会话保持）【需要代码】

30 秒「电梯句」\
“分享链接 `/share/{shareId}` 任何人可访问，**首次必须输入 5 位提取码**；前端调用 `/checkShareCode` 验证成功后，后端把 `{shareId, codeMd5}` 写进 **session**，后续刷新页面、切换目录、下载文件**同一 session 内免码**；关闭浏览器或 session 过期（30 min）再次访问需重新输入。”

***

2 分钟「细节+亮点」

1.  分享码校验

    *   组件 `ShareCheck.vue` 输入 5 位码 → 调 `/showShare/checkShareCode`：\
        – 后端比对 **code 哈希**（防明文存储）；\
        – 正确 → `session.setAttribute("share_access_" + shareId, true)` 并返回 200；\
        – 错误 → 返回 401，前端弹“提取码错误”。
2.  会话保持

    *   后续所有分享接口（列表、下载、保存到网盘）**统一带 JSESSIONID**；
    *   后端拦截器 `ShareAccessInterceptor`：

        ```javascript
        if (session.getAttribute("share_access_" + shareId) == null) 
            throw new ShareCodeException();
        ```

        **无码直接 403**。
3.  免分享码进入文件列表

    *   `Share.vue` 在 `onMounted` 先调 `/getShareLoginInfo`：\
        – 返回 200 → 已校验过，**直接渲染文件列表**；\
        – 返回 403 → 路由跳 `/shareCheck/{shareId}` 让用户输码，**自动回退**。
4.  前端无侵入

    *   所有分享相关 axios 请求 **withCredentials=true**（已统一封装），**自动带 Cookie**；
    *   分享页无 Vuex 状态，**刷新后仍认 session**，不怕 F5。
5.  安全加固

    *   分享码 5 位 **数字+字母随机**，**1 万次撞库概率 < 0.01 %**；
    *   后端限制 **单 IP 每天最多 20 次错误码**，**防止爆破**；
    *   session 30 min 无操作过期，**再访问需重新输码**。

***

追问 1：「用户复制链接给别人，别人浏览器打不开是否还要输码？」\
化解：\
“**只要 session 里没有 `share_access_*` 就要输码**；不同浏览器 Cookie 不同，**天然隔离**。”

***

追问 2：「关闭浏览器后重新打开链接，为什么又要输码？」\
化解：\
“**JSESSIONID 是临时 Cookie**，关浏览器即失效；这是有意设计，**防止分享码被中间人长期复用**。”

***

追问 3：「如果用户想‘永久免码’怎么办？」\
化解：\
“**不提供永久免码**。可让分享者把提取码直接写在链接后面 `?code=ABCDE`，前端 `onMounted` 自动读 query 调校验接口，**一次校验仍写 session**，体验一样但**安全可控**。”

***

追问 4：「session 存在服务端，分布式节点怎么做共享？」\
化解：\
“生产环境用 **Redis Session**，`spring-session-data-redis` 把 `share_access_*` 存 Redis，**多节点共享**，**零代码改动**。”

# 7.大文件下载（断点续载、速度控制）【需要代码】

“点击下载先调 `/createDownloadUrl` 拿到一次性 `downloadId`（有效期 5 min），再 `window.location.href = /api/file/download/{downloadId}` 让浏览器直接接管；后端返回 `Content-Disposition: attachment` 流式下载，**不走前端内存**，支持 GB 级大文件；失败或过期 404，前端弹‘下载链接已失效’。”

***

2 分钟「细节+亮点」

1.  一次性下载地址

    *   前端：

        JavaScript复制

            const result = await proxy.Request({ url: api.createDownloadUrl + "/" + fileId });
            window.location.href = api.download + "/" + result.data;
    *   后端：\
        – 生成 16 位随机 `downloadId` → 写 Redis，**TTL=5 min**；\
        – 记录 `fileId、userId、expireAt`**，防越权**。
2.  流式响应

    *   Spring 用 `InputStreamResource` 块读取：

        java复制

            response.setHeader("Content-Disposition","attachment; filename*=UTF-8''" + URLEncoder.encode(fileName, "UTF-8"));
            IOUtils.copyLarge(inputStream, response.getOutputStream());

        **内存只占 64 KB 缓冲区**，**4 GB 文件也能下**；
    *   支持 **HTTP Range**（代码已预留），**后续可断点续载**。
3.  权限校验

    *   拦截器先验 `downloadId` 存在且未过期 → 再验 `userId` 与当前登录用户一致 → 最后验文件归属；
    *   **三步都过才开始读流**，**防止盗链**。
4.  前端零内存

    *   用 `window.location` 而不用 `axios.get(..., {responseType: 'blob'})`，**浏览器分段写入磁盘**，**不会把整个文件吃进内存**；
    *   下载进度由浏览器原生展示，**UI 无额外开发**。
5.  失败处理

    *   404 → “下载链接已失效或文件已被删除”；
    *   403 → “无权限下载此文件”；
    *   前端统一弹 toast，**不弹窗阻断**。

***

追问 1：「为什么不用 Blob 下载？那样可以显示自定义进度条。」\
化解：\
“Blob 要把整个文件读进内存，**超过 2 GB 浏览器直接崩溃**；用 location 流式下载**不占内存**，**GB 级文件无压力**；进度条后续可改 **Stream API + fetch** 做流式进度，目前先保证稳定。”

***

追问 2：「下载中用户关页面，会断吗？」\
化解：\
“**不会**。浏览器多线程下载，**与标签页生命周期无关**；关页面后下载仍在后台跑，**用户去下载列表能看到**。”

***

追问 3：「一次性 downloadId 5 min 太短，用户慢网速下不完怎么办？」\
化解：\
“**5 min 只是鉴权窗口**，真正下载一旦开始**不受时间限制**；只要 TCP 连接不断，**4 小时也能下完**；如果真断网，后续上断点续载即可。”

***

追问 4：「多人同时下载同一个大文件，服务器带宽被打满怎么办？」\
化解：\
“后端用 **令牌桶限速 200KB/s** 每人；**CDN 回源**做边缘缓存，**热点文件走 CDN 流量**，源站只算首次回源，**成本 ×10 倍下降**。”

# 8.用户空间配额控制（前端实时条 + 后端校验）【需要代码】

30 秒「电梯句」\
“顶部实时空间条调 `/getUseSpace` 返回 `{useSpace, totalSpace}`，用 el-progress 百分比展示，**保留两位小数**；任何上传/删除/保存他人分享完成都会重新拉接口，**1 秒内同步**；上传前前端先 `useSpace + fileSize > totalSpace` 拦截，**提前弹层提示‘空间不足’并引导清理**。”

***

2 分钟「细节+亮点」

1.  数据获取

    *   入口：`Framework.vue` `onMounted` 调 `getUseSpace()`；
    *   返回字段：

        JSON复制

            { useSpace: 8293910392, totalSpace: 10737418240 }
    *   计算百分比：

        JavaScript复制

            Math.floor((useSpace / totalSpace) * 10000) / 100   // 保留两位小数
2.  实时同步

    *   上传完成 `uploadCallbackHandler()` → 主动再调 `getUseSpace()`；
    *   删除、保存他人分享、新建文件夹等操作 → 父组件 emit `@reload="getUseSpace"`；
    *   **1 秒内进度条重新渲染**，用户感知“立刻更新”。
3.  前端拦截

    *   上传前 `addFile()` 里：

        JavaScript复制

            if (file.size + useSpaceInfo.value.useSpace > useSpaceInfo.value.totalSpace) {
                proxy.Confirm('空间不足，是否前往清理？', () => router.push('/recycle'));
                return;
            }

        **提前终止上传**，**减少一次无用请求**。
4.  后端双层校验

    *   上传第一片时后端再验：

        sql复制

            select sum(file_size) from user_file where user_id = ?

        **超配额直接 413**，**前端 fallback 弹“空间不足”**；
    *   **并发上传也安全**，**同一用户同时 10 个分片也过不了**。
5.  超配额引导

    *   空间条下方放「清理」图标，点击直达回收站；
    *   配额用 `proxy.Utils.size2Str` 显示成 **“7.73 GB / 10 GB”**，**直观可读**。

***

追问 1：「百分比只保留两位，文件 1 KB 级别变化根本看不出来？」\
化解：\
“**进度条是视觉参考**，**真正精准值 hover 会显示 `useSpace/totalSpace` 字符串**；若用户需要更细粒度，**点击‘刷新’图标会重新拉接口**，**小数点后两位实时更新**。”

***

追问 2：「并发上传 10 个大文件，前端拦不住怎么办？」\
化解：\
“**前端拦第一道**，**后端再拦第二道**；第一片上传前后端原子 SQL 累加已用空间，**超 413 立即返回**，**所有并发片全部失败**，**用户弹‘空间不足’**。”

***

追问 3：「空间条 1 秒一刷，用户狂点上传会不会打爆服务器？」\
化解：\
“**只在操作完成后拉一次**，**不会定时轮询**；1 秒是‘上传完成 → 收到回调 → 立即拉’，**正常用户间隔 >1 s**，**QPS 可控**。”

***

追问 4：「以后做会员系统，空间动态变更怎么做到实时？」\
化解：\
“**后端改配额后同时 publish 一条 MQ 消息**；前端 WebSocket 推送新 `totalSpace`，**进度条无刷新瞬移**；**代码层只改一行 totalSpace 赋值**。”

# 9.超管文件管理（跨用户下载、删除）【需要代码】

“超管列表接口 `/admin/loadFileList` 返回所有用户文件，每条数据带 `userId_fileId` 复合主键；下载时把 `userId` 拼进 `/admin/createDownloadUrl/{userId}/{fileId}`，后端用 **管理员 token** 直接生成下载地址，**无需用户登录态**；删除同理，传 `userId_fileId` 数组，后端**跳过用户归属校验**物理删除，同时记录操作日志。”

***

2 分钟「细节+亮点」

1.  复合主键设计

    *   前端：

        JavaScript复制

            selectFileIdList.push(row.userId + "_" + row.fileId);
    *   后端：\
        – `String[] userIdFileId = fileIdAndUserIds.split(",");`\
        – 每段再 `split("_")` 拿到 `userId` 与 `fileId`，**避免主键冲突**。
2.  跨用户下载

    *   API 路由：

        http复制

            POST /admin/createDownloadUrl/{userId}/{fileId}
    *   后端：\
        – 用 **超管角色** 直接查 `user_file` 表，**不校验当前登录者是否拥有该文件**；\
        – 生成 **一次性 downloadId**（TTL=5 min）→ 返回给前端 → `window.location.href = /api/admin/download/{downloadId}`；\
        – **流式下载**，**内存零拷贝**，**GB 级文件无压力**。
3.  跨用户删除

    *   批量参数：

        JavaScript复制

            params: { fileIdAndUserIds: "1001_2001,1002_2002" }
    *   后端：\
        – 循环 `delete from user_file where user_id=? and file_id=?`；\
        – 同时 **物理删除磁盘文件**（若本地存储）或 **调用 OSS 删除 API**；\
        – 写 `admin_operation_log`（操作人、目标用户、文件、时间），**审计追踪**。
4.  权限兜底

    *   拦截器：\
        – 校验 `userInfo.roleType == 1`，**非超管 403**；\
        – 校验 `userId` 存在，**防止传空串误删全表**；
    *   前端：\
        – 按钮仅超管可见（`v-if="userInfo.admin"`），**普通用户无入口**。
5.  前端复用

    *   与普通文件列表 **同一套 UI**（`FileList.vue`），**只换 API 前缀**；
    *   通过 `props.adminShow=true` 控制列显（**多一列“发布人”**），**零重复代码**。

***

追问 1：「超管误删重要文件怎么恢复？」\
化解：\
“**表加 is\_deleted 软删除字段**，**删除只是改状态**；同时写 **回收站表**（admin\_recycle），**记录原路径与操作人**；**10 天内可在回收站一键还原**。”

***

追问 2：「下载时 userId 被篡改，会不会下到别人的私密文件？」\
化解：\
“**后端再次校验 userId+fileId 是否存在**，**不存在 404**；**downloadId 一次性 5 min 过期**，**无法重放**。”

***

追问 3：「并发批量删除 1k 个文件，接口超时怎么办？」\
化解：\
“**后端改异步** → 收到请求立即返回任务 ID，**用线程池分批删除**，**前端轮询进度**；**超管看到‘删除中’状态**，**不会一直转圈**。”

***

追问 4：「磁盘文件与数据库记录不一致怎么兜底？」\
化解：\
“**先删数据库**，**成功后再删磁盘/OSS**；**磁盘删失败抛异常**，**数据库事务回滚**；\*\* nightly job 对比 DB vs 磁盘\*\*，**多退少补**。”

# 10.回收站文件还原（原父目录被删的兜底）【需要代码】

“回收站还原调 `/recycle/recoverFile` 只传 `fileIds`，后端先根据软删记录里的 `original_file_pid` 找原目录；**若原目录不存在**，自动把文件挂到『**我的网盘/恢复的文件**』这个兜底目录并返回新 `filePid`\*\*，前端弹提示‘已移至恢复目录’，**用户零失败感知**。”

***

2 分钟「细节+亮点」

1.  软删时留痕

    *   表 `user_file` 增加字段：\
        `delete_type=2`（回收站）、`delete_time`、`original_file_pid`（**被删时的父级 ID**）、`original_file_name`（**防止重名冲突**）。
    *   删除接口只做 **UPDATE** 状态，**不物理删**，**保留所有路径信息**。
2.  还原主流程

    *   后端逻辑（单条/批量同一事务）：

        1.  根据 `fileId` 查 `original_file_pid`；
        2.  `SELECT COUNT(*) FROM user_file WHERE file_id = original_file_pid AND delete_type=0`；
        3.  **存在** → 直接 `UPDATE delete_type=0, delete_time=null`；
        4.  **不存在** → 调用 `getOrCreateRecoverFolder(userId)` → 拿到固定名称『恢复的文件』目录 `folderId`，**把 `original_file_pid` 替换成该 folderId 再还原**；
        5.  返回结果里带 `newParentName: "恢复的文件"`，**供前端提示**。
3.  兜底目录规则

    *   路径：`/我的网盘/恢复的文件`（**folderId 固定查缓存**）；
    *   不存在则自动创建，`user_id=当前用户`、`file_type=0`、`folderType=1`；
    *   **同名文件冲突** → 自动重命名 `原文件名(1).后缀`，**返回新文件名**。
4.  前端提示

    *   只要有任何一条返回 `newParentName` ≠ null，**弹 ElMessage.warning('部分文件原目录已不存在，已移至“恢复的文件”')**；
    *   无 `newParentName` → 静默成功，**用户感知就是“一键还原”**。
5.  并发 & 幂等

    *   还原接口 **幂等**：同一条回收站记录重复调返回 **“已还原”**；
    *   事务内加 **行锁 `FOR UPDATE`**，**防止并发还原导致空间重复计算**。

***

追问 1：「原目录被还原后又把文件拖进去，会不会重复？」\
化解：\
“**不会**。还原时 **file\_pid 已更新为真实存在的新目录**，**路径正常**，**用户可任意移动**；**兜底目录只当‘临时收容所’**。”

***

追问 2：『恢复的文件』目录被用户误删怎么办？」\
化解：\
“**再还原时若发现兜底目录也被删**，**会重新创建**；**目录名固定**，**创建后把 ID 写缓存**，**下次复用**。”

***

追问 3：「批量还原 1k 条，原父目录缺失性能怎么保证？」\
化解：\
“**先 SELECT 一批 original\_file\_pid**，**IN 查询判断存在性**，**缺失的批量插到恢复目录**；**1k 条 < 100 ms**；**异步返回任务 ID**，**前端轮询进度**。”

***

追问 4：「怎么防止用户利用‘反复删-还原’刷空间计数？」\
化解：\
“**空间只算非软删记录**；**delete\_type=0 才累加**，**还原只是把状态改回 0**，**空间总额不变**，**无漏洞可刷**。”
